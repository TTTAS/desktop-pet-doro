## 🎯 核心教訓

### 教訓 1：過度工程化比欠缺架構更危險

**問題：** 我們為一個桌面寵物應用實施了 5 層架構（資料層、領域層、應用層、UI 層、基礎設施層），這是大型企業應用的模式。

**後果：**
- 簡單的狀態變更需要經過 4-5 個組件
- 代碼追蹤困難，debug 時間變長
- 新功能開發速度變慢（需要修改多層）
- 認知負擔增加（需要理解整個架構）

**正確做法：**
```
小型專案（< 5000 行） → 3 層架構足夠
  - UI 層（視圖和互動）
  - 業務層（邏輯和狀態）
  - 資料層（持久化）

大型專案（> 20000 行） → 才考慮 5 層架構
```

---

### 教訓 2：抽象應該來自需求，而非假設

**問題：** 我們創建了 `MovementWindowPort` Protocol，但只有一個實現（`DoroWindow`）。

**原因：** 為了「未來可能需要多個實現」而過早抽象。

**正確做法：**
```python
# ❌ 錯誤：過早抽象
class MovementWindowPort(Protocol):
    def current_position(self) -> QtCore.QPoint: ...
    # ... 6 個方法

# ✅ 正確：直接依賴
class MovementManager:
    def __init__(self, window: DoroWindow):
        self._window = window
```

**YAGNI 原則：** You Aren't Gonna Need It — 在真正需要之前不要添加功能。

---

### 教訓 3：信號/槽不是銀彈

**問題：** BubbleController 有 8 個信號，CoreManager 有 10+ 個信號。

**後果：**
- 數據流變成「信號湯」（Signal Soup）
- Debug 時難以追蹤事件源頭
- 性能開銷（Qt 信號機制有成本）

**正確使用原則：**
```
✅ 跨層通信（UI 層 ← 業務層） → 使用信號
✅ 異步操作完成通知 → 使用信號
❌ 同層內組件調用 → 直接調用方法
❌ 簡單的 getter/setter → 直接訪問
```

**重構前：** 8 個信號
```python
text_changed = Signal(str, bool)
visibility_changed = Signal(bool)
offset_changed = Signal(QtCore.QPointF)
scale_changed = Signal(float)
repaint_requested = Signal()
cursor_unset_requested = Signal()
update_bubble_side_requested = Signal()
state_settings_apply_requested = Signal(str)
```

**重構後：** 應該合併成 2-3 個
```python
bubble_state_changed = Signal(dict)  # 包含所有狀態
repaint_requested = Signal()
```

### 教訓 4：God Object 問題需要分而治之

**問題：** StateService 有 753 行，職責包括：
- 狀態管理
- GIF 管理
- 移動狀態管理
- 轉換管理
- 狀態解析

**為什麼沒有拆分：** 重構時創建了 CoreManager，但 StateService 本身沒有改善。

**正確拆分方式：**
```
StateService (150 行)
  - 核心狀態 CRUD
  - 當前狀態追蹤

GifService (100 行)
  - GIF 資源管理

TransitionService (100 行)
  - 轉換邏輯

MovementStateService (80 行)
  - 移動狀態管理
```

**單一職責原則：** 一個類應該只有一個改變的理由。

---

### 教訓 5：文檔過多 = 規劃過度

**問題：** docs/ 有 38 個文檔，包括多個 PHASE 計劃、審計報告、提案。

**後果：**
- 花太多時間寫文檔，而不是寫代碼
- 文檔互相矛盾（舊的沒刪除）
- 新人閱讀困難（不知道哪個是最新的）

**正確做法：**
```
保留的文檔（< 10 個）：
  - README.md（專案介紹）
  - ARCHITECTURE.md（當前架構）
  - BEST_PRACTICES.md（教訓總結）
  - CHANGELOG.md（變更記錄）
  - TESTING.md（測試指南）

刪除的文檔：
  - 所有過時的 PHASE 計劃
  - 所有審計報告（AUDIT.md）
  - 所有提案（PROPOSAL.md）
  - 所有 TODO（已完成或過時）
```

**原則：** 代碼是真相，文檔是輔助。過時的文檔比沒有文檔更糟糕。

## 📊 規模與複雜度對照

### 專案規模分類

| 規模 | 代碼行數 | 文件數 | 建議架構 | 範例 |
|------|---------|--------|---------|------|
| **微型** | < 500 | < 5 | 單文件或簡單模塊 | 腳本、工具 |
| **小型** | 500-5000 | 5-20 | 3 層架構 | Doro（當前） |
| **中型** | 5000-20000 | 20-50 | 3-4 層架構 | 中型企業應用 |
| **大型** | 20000-100000 | 50-200 | 5 層架構 + 微服務 | 大型系統 |
| **超大型** | > 100000 | > 200 | 分布式架構 | 企業平台 |

### Doro 專案現狀

- **代碼行數：** ~8000 行（估算）
- **文件數：** 66 個應用文件 + 35 個測試
- **當前架構：** 5 層
- **建議架構：** 3 層
- **結論：** 過度工程化

## 🏗️ 架構設計原則

### 原則 1：從簡單開始，按需演化

```
階段 1（初期）：單文件或模塊
  ↓ 當文件 > 500 行時
階段 2（成長）：基本分層（UI / Logic / Data）
  ↓ 當業務邏輯複雜時
階段 3（成熟）：完整分層（加入 Service 層）
  ↓ 當需要多團隊協作時
階段 4（企業）：領域驅動設計（DDD）
```

**不要跳過階段！** Doro 從階段 1 直接跳到階段 4，這是錯誤的。

---

### 原則 2：依賴方向要單向

```
✅ 正確的依賴方向（由上到下）：
UI 層
  ↓ 依賴
業務層
  ↓ 依賴
資料層

❌ 循環依賴（必須避免）：
UI 層 ←→ 業務層
```

**依賴反轉原則（DIP）：** 高層模塊不應該依賴低層模塊，兩者都應該依賴抽象。

但注意：**小專案不需要過度使用依賴反轉**。

---

### 原則 3：合理使用設計模式

| 模式 | 適用場景 | 不適用場景 |
|------|---------|-----------|
| **Repository** | 多種資料來源（DB + API + File） | 只有一種資料來源 |
| **Service Layer** | 複雜業務邏輯，多個用例 | 簡單 CRUD |
| **Observer (Signal/Slot)** | 跨層通信、異步事件 | 同層調用、同步操作 |
| **Strategy** | 多種算法可互換 | 只有一種實現 |
| **Factory** | 創建邏輯複雜、多種類型 | 簡單的 `new` 就夠 |
| **Protocol (Interface)** | 多個實現、需要 mock | 只有一個實現 |

**Doro 的誤用：**
- ❌ Repository — 只有 JSON 文件
- ❌ Protocol — 只有一個實現
- ⚠️ Service Layer — 過度細分（Orchestrator + Controller + Service）

---

### 原則 4：測試先行，重構有底氣

```python
# 重構前的檢查清單：
□ 測試覆蓋率 > 80%
□ 所有核心功能有測試
□ CI/CD 自動運行測試

# Doro 的問題：
✗ 測試覆蓋率未知（pytest-cov 被禁用）
✗ 重構時沒有測試保護
✗ 不知道重構是否破壞功能
```

**教訓：** 沒有測試的重構 = 賭博。

## ✅ 重構檢查清單

### 重構前（Pre-Refactoring）

- [ ] **確定重構目標** — 解決什麼問題？帶來什麼價值？
- [ ] **測試覆蓋率 > 80%** — 否則先寫測試
- [ ] **記錄當前架構** — 拍照留底（架構圖）
- [ ] **評估風險** — 會影響哪些模塊？
- [ ] **時間預估** — 小型重構 < 1 天，大型重構 < 1 週

### 重構中（During Refactoring）

- [ ] **小步快跑** — 每次提交只改一件事
- [ ] **每步都測試** — 改完立即運行測試
- [ ] **保持功能不變** — 重構不改變外部行為
- [ ] **避免同時重構和加新功能** — 一次只做一件事
- [ ] **及時提交** — 每個穩定狀態都 commit

### 重構後（Post-Refactoring）

- [ ] **所有測試通過** — 100% 通過
- [ ] **性能不下降** — 對比重構前後
- [ ] **代碼覆蓋率不下降** — 甚至應該提升
- [ ] **文檔更新** — 架構圖、README
- [ ] **刪除舊代碼** — 不要保留「向後兼容」超過 2 週
- [ ] **Code Review** — 如果是團隊項目

## 🔧 技術債管理

### 識別技術債

Doro 當前的技術債：

| 技術債 | 嚴重程度 | 影響範圍 | 償還期限 |
|--------|---------|---------|---------|
| 雙重配置系統（QSettings + ConfigManager） | 🔴 高 | 全專案 | 1 週內 |
| StateService God Object（753 行） | 🔴 高 | 核心邏輯 | 1 個月內 |
| 向後兼容代碼（wire_dependencies） | 🟡 中 | DoroApp | 2 週內 |
| 測試覆蓋率未知 | 🟡 中 | 測試品質 | 立即 |
| 信號過多（Signal Soup） | 🟡 中 | 可維護性 | 1 個月內 |
| 過時文檔（38 → 10） | 🟢 低 | 新人理解 | 立即 |

### 償還策略

```python
# ❌ 錯誤：累積技術債
if new_config_manager:
    value = new_config_manager.get()
else:
    value = old_config.get()  # 「以後再改」

# ✅ 正確：立即遷移或設定期限
# TODO(2024-12-20): 移除舊配置系統
if new_config_manager:
    value = new_config_manager.get()
else:
    # 遷移邏輯
    migrate_to_new_config()
    value = new_config_manager.get()
```

**原則：** 技術債要麼立即償還，要麼設定明確期限。「以後再說」= 永遠不會做。

## ⚠️ 常見陷阱

### 陷阱 1：「為了解耦而解耦」

```python
# ❌ 過度解耦
class BubbleController:
    text_changed = Signal(str, bool)
    visibility_changed = Signal(bool)
    offset_changed = Signal(QtCore.QPointF)
    # ... 8 個信號

# ✅ 合理耦合
class BubbleController:
    def set_text(self, text: str):
        self._text = text
        self._window.update_bubble()  # 直接調用
```

**何時解耦：** 當組件需要替換、測試、或跨進程通信時。

**何時耦合：** 當組件永遠只有一個實現，且在同一進程內。

---

### 陷阱 2：「企業級模式適用於所有專案」

**錯誤認知：**
- Repository 模式很好 → 我應該用
- DDD 是最佳實踐 → 我應該學
- 5 層架構很清晰 → 我應該實施

**正確認知：**
- Repository 模式很好 → **當我有多種資料來源時**才用
- DDD 是最佳實踐 → **當業務邏輯非常複雜時**才用
- 5 層架構很清晰 → **當專案 > 20000 行時**才用

**原則：** 模式是工具，不是目標。根據問題選工具，不是為了用工具而造問題。

---

### 陷阱 3：「追求完美架構」

```
完美主義者的重構循環：
  發現架構問題
    ↓
  制定宏大重構計劃（5 個 PHASE）
    ↓
  寫大量設計文檔（PROPOSAL, PLAN, AUDIT）
    ↓
  開始重構
    ↓
  發現新問題
    ↓
  制定新計劃 ←─ 循環
    ↓
  專案永遠在重構，功能永遠沒完成
```

**正確做法：**
```
實用主義者的迭代改進：
  發現問題 → 評估影響 → 快速修復 → 測試 → 完成
  ↓
  繼續開發功能
```

**原則：** 完成比完美更重要。Good enough is good enough.

---

### 陷阱 4：「重構等於重寫」

```python
# ❌ 大爆炸式重構（Big Bang Refactoring）
# 一次性改變整個架構，風險極高

# ✅ 漸進式重構（Incremental Refactoring）
# 每次只改一小部分，保持系統可運行
```

**教訓：** Doro 的重構創建了 CoreManager，但保留了大量「向後兼容」代碼。這是中間狀態，應該盡快完成遷移。

## 🎓 學習建議

### 對於個人專案（如 Doro）

1. **優先順序：** 功能完整 > 代碼品質 > 架構完美
2. **測試策略：** 核心邏輯 100% 覆蓋，UI 層選擇性測試
3. **文檔策略：** README + 簡單架構圖即可
4. **重構時機：** 當痛點明顯時（難以添加新功能、bug 頻繁）

### 對於團隊專案

1. **優先順序：** 可維護性 > 功能速度 > 架構完美
2. **測試策略：** 所有層級都要測試，CI/CD 自動化
3. **文檔策略：** 完整的 API 文檔、架構決策記錄（ADR）
4. **重構時機：** 定期重構（每個 Sprint）

## 🎯 總結

### 最重要的三個教訓

1. **簡單優於複雜** — 過度工程化比欠缺架構更危險
2. **測試先行** — 沒有測試的重構是賭博
3. **按需演化** — 不要為未來的需求過早設計
