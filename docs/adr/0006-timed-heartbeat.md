# ADR 0006：定時心跳只做角色表現

- 狀態：採用
- 日期：2026-10-08

## 背景

ADR 0002 有兩層活潑：基本活潑（隨機、不呼叫模型）與情境活潑（分頁事件觸發）。兩層都不會「隔一段時間主動想想要不要找使用者」。OpenClaw 的 heartbeat 做的就是這件事：Gateway 的排程器每 30 分鐘把一段固定提示詞送給模型，模型照清單檢查，沒事回 `NO_REPLY`。我們評估過直接接 OpenClaw，結論見 `docs/TODO_OPEN_CLAW.md`：不接 Node.js，改用 Python 內化機制。

## 決策

- 新增第三層「定時心跳」`HeartbeatController`，不取代前兩層。Doro 的 Qt 事件迴圈加 `QTimer` 就是排程器。
- 預設關閉；開啟後預設每 30 分鐘一次，1～1440 分鐘可調。每次心跳都是一次模型請求，同時最多一個。
- 下列情況跳過，不呼叫模型：安靜陪伴、忙碌（聊天、拖曳、選單、動作、轉場、網頁工作、畫面上還有泡泡）、上一次心跳未結束、90 秒內有互動、系統閒置 10 分鐘以上（Windows `GetLastInputInfo`；其他平台只看 Doro 互動）。只因忙碌而跳過的排程心跳，20 秒後重試一次。
- 給模型的資料：時間與星期、距上次互動多久、最近 6 則聊天、使用者可編輯的心跳清單（`heartbeat.md`，UTF-8，`#` 開頭為說明；不是 UTF-8 時跳過並提示重新存檔）、心跳日誌（最近 8 次心跳的時間與台詞）、有效分享分頁的標題。全部標成資料，不是指令。
- 回覆結構為 `HeartbeatReply`：`worth_saying`、`state`、`line`、`move`，**沒有 `tool` 欄位**。格式上就寫不出上網、查證或操作；模型硬塞的 `tool` 在驗證時被丟掉（延續 ADR 0004、0005）。
- 開口判斷沿用 `worth_saying`，不使用 `[SILENT]` 字串。說話走 `present_structured_reply`；Doro 忙時最多等 120 秒，期間使用者互動、進入安靜模式或結果過期就不發言。
- 失效時機：使用者訊息在任何路徑被接受（`ChatOrchestrator.user_message_accepted`，含一般聊天、分頁提問、網頁指令與操作確認）、按住或拖曳 Doro、切換安靜模式；心跳看過分頁 A 而現在已不是 A。只是聊天輸入列取得焦點或展開時，算忙碌、心跳延後，不讓結果失效。
- 結果回來時先檢查是否過時，再處理成功、沉默或失敗；過時就連手動心跳的失敗／沉默提示也不顯示。真正發言前再檢查一次。
- 心跳日誌只記 Doro 自己的輸出（含「沒開口」），跨重啟保留，用來避免重複；它不是長期記憶。
- 右鍵「立刻跳一次心跳」：略過開關、近期互動與系統閒置檢查（使用者正在按選單），仍遵守安靜、忙碌與一次一個；跳過或沉默時用泡泡告知。

## 考慮過的選項

- 接 OpenClaw Gateway：多一個 Node.js 常駐服務與第二個大腦，權限模型也不同。否決。
- 用提示詞要求「心跳不要用工具」：小模型不一定遵守。改用沒有 `tool` 的結構。
- 先做長期記憶再做心跳（TODO 原順序）：延後看到效果。改為心跳先行，以心跳清單提供目標、心跳日誌避免重複。
- 接 MCP 讓心跳讀行事曆：會穿過 ADR 0004 的安全牆，留待另外設計。
- 定時提醒（cron）、執行腳本、回到電腦前打招呼、話量設定、心跳紀錄視窗：v1 不做，記在 TODO。

## 結果與限制

- 心跳是否開口取決於使用者設定的模型；保守的任務說明只能降低、不能保證不會說無意義的話。
- 系統閒置偵測只在 Windows 有效；其他平台人不在時仍可能心跳。
- 只因忙碌跳過時會重試；其他原因跳過就等下一個間隔，不補跳。
- 心跳日誌是本機 JSON，清單是本機 Markdown，都放在 Doro 使用者資料夾（與 `presence.json` 同處）。
